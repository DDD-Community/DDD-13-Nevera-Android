# Compose 화면 설계: Screen/Content 분리와 이벤트 처리 방식

## 문서의 목적과 전제

이 문서는 신규(Flutter → Android Native 전환) 프로젝트의 Presentation Layer 계층 구조를 설계하기 위한 판단 근거를 정리합니다.

의도적으로 특정 기존 프로젝트의 관행을 근거로 삼지 않습니다. 이미 그렇게 짜여 있는 코드를 근거로 "우리가 이렇게 하고 있으니 맞다"고 결론 내리면 확증편향이 됩니다. 대신 Jetpack Compose가 공식적으로 권장하는 설계 원칙과, Android 커뮤니티에서 실제로 의견이 갈리는 지점을 그대로 드러낸 뒤, 신규 프로젝트의 조건(대규모 마이그레이션, 다인원, 장기 유지보수)에 맞춰 어떤 선택이 합리적인지 판단합니다. 기존 사내 프로젝트(Nevera)의 구현은 "이 원칙을 코드로 옮긴 하나의 사례"로만 뒤쪽에 첨부합니다.

결론은 팀이 논의해 확정해야 할 권장안이지, 유일한 정답이 아닙니다.

## 1. 질문 정의

1. `Screen`이 상태 구독부터 렌더링까지 전부 담당하는 것과, 상태 구독을 담당하는 계층(`Screen`)과 순수 렌더링을 담당하는 계층(`Content`)을 나누는 것 — 어느 쪽이 더 합리적인가.
2. Navigation, Toast, Dialog, BottomSheet처럼 "한 번 발생하고 끝나는" 이벤트는 어떤 계층에서 다뤄야 하는가.

## 2. Stateful/Stateless 분리 원칙

### 2.1 근거: State Hoisting

Compose 공식 아키텍처 가이드는 "state hoisting(상태 끌어올리기)"이라는 패턴을 명시적으로 권장합니다. 핵심은 하나입니다 — **상태를 소유하고 변경하는 컴포저블(stateful)과, 그 상태를 파라미터로 받아 그리기만 하는 컴포저블(stateless)을 분리한다.** 이때 stateless 컴포저블이 얻는 성질로 보통 다음 네 가지가 꼽힙니다.

- **Single source of truth**: 상태가 한 곳에만 존재하고 중복되지 않습니다.
- **Shareable**: 같은 상태를 여러 컴포저블이 서로 다른 방식으로 렌더링할 수 있습니다.
- **Interceptable**: 상태를 소유한 상위 계층이 값이 실제로 바뀌기 전에 로직을 개입시킬 수 있습니다.
- **Decoupled**: stateless 컴포저블은 상태가 어디서 오는지 몰라도 되므로, ViewModel이든 고정값이든 상관없이 재사용됩니다.

이 프로젝트에서 논의 중인 `Screen`(ViewModel을 구독하는 stateful 진입점) / `Content`(값과 콜백만 받는 stateless 렌더러) 구조는, 어떤 특정 회사나 프로젝트가 고안한 패턴이 아니라 **이 표준 원칙에 화면 단위 이름을 붙인 것**입니다. 따라서 이 논의의 본질은 "Screen/Content를 나눌지 말지"가 아니라 **"화면 단위에서도 stateful/stateless 분리를 지킬 것인지"**입니다.

### 2.2 분리가 주는 이득

State Hoisting의 일반적 이득(위 4가지) 외에, 화면 단위 분리가 실무에서 주는 이득은 다음과 같습니다.

| 이득 | 설명 |
|---|---|
| Preview 가능성 | Stateless 컴포저블은 `ViewModel`/`NavController`/`Context` 없이 값만 주입해 렌더링을 확인할 수 있습니다. |
| 테스트 용이성 | Compose UI 테스트에서 ViewModel을 모킹하지 않고 고정된 State 값으로 렌더링 결과를 검증할 수 있습니다. |
| Recomposition 범위 제어 | Stateful 계층의 로컬 상태(다이얼로그 visibility 등) 변경이 stateless 계층까지 전파되지 않아, 불필요한 재구성을 줄일 수 있습니다. |
| 플랫폼 의존성 격리 | `Context`, 권한 조회, `ActivityResultLauncher` 같은 비결정적 코드가 stateful 계층 한 곳에 모입니다. |

### 2.3 분리에 드는 비용

이 이득은 공짜가 아닙니다.

- 컴포저블 함수와 파일이 하나 늘고, 값을 파라미터로 다시 전달해야 합니다(prop drilling).
- 계층이 깊어질수록 상태와 콜백을 여러 단계에 걸쳐 전달해야 하는 부담이 커집니다.
- 화면이 실제로 단순하다면(정적 텍스트, 상태 없음) 이 분리가 주는 이득 대비 코드량 증가가 아깝게 느껴질 수 있습니다.

### 2.4 분리하지 않는 것이 합리적인 경우

객관적으로 인정해야 할 반대 근거도 있습니다.

- **프로토타입/스파이크 코드**: 정식 구조를 갖출 필요가 없는 검증용 코드.
- **완전히 정적인 화면**: 상태 자체가 없거나(약관 화면 등) ViewModel 없이도 그려지는 화면은 분리해도 얻는 이득이 제한적입니다.
- **팀이 아직 Compose에 익숙하지 않은 초기 단계**: 레이어가 늘어나는 만큼 온보딩 비용도 함께 늘어납니다. 마이그레이션 초반에는 오히려 학습 곡선을 완만하게 만드는 것이 더 급할 수 있습니다.

### 2.5 대규모 마이그레이션 프로젝트에서 이 판단에 영향을 주는 요인

이 구조의 가치는 "구조 자체가 옳은가"보다 **"이 구조를 실제로 활용하는 프로세스에 팀이 투자하는가"**에 크게 좌우됩니다. 다음 질문들이 판단에 영향을 줍니다.

- 여러 인원이 장기간 유지보수할 코드베이스인가? → 예측 가능한 구조의 가치가 인원·기간에 비례해 커집니다. 마이그레이션 프로젝트는 대체로 여기에 해당합니다.
- Preview를 실제 디자인 리뷰·QA 프로세스에 쓸 계획이 있는가? → Preview를 안 본다면 stateless 분리의 핵심 이득 하나가 사라집니다.
- Compose UI 테스트/스크린샷 테스트에 투자할 계획이 있는가? → 마찬가지로 테스트를 안 짠다면 "테스트 용이성"이라는 이득은 이론상의 가치로만 남습니다.
- 팀이 스캐폴드/린트로 컨벤션을 강제할 수 있는가? → 강제 수단이 없으면 "예외"가 하나둘 생기고, 예외가 늘어날수록 "왜 이 화면만 다른가"를 추론하는 비용이 분리 자체의 이득을 잠식합니다.

### 2.6 판단 기준

| 조건 | 권장 |
|---|---|
| 다인원·장기 유지보수, Preview/테스트 인프라 투자 계획 있음 | 기본값으로 항상 분리 |
| 소수 인원·단기 프로젝트, Preview/테스트를 실제로 쓰지 않음 | 분리의 이득이 제한적 — 팀 판단에 맡기되 강제하지 않음 |
| 프로토타입/스파이크 | 분리하지 않음 |

Flutter → Native 마이그레이션처럼 다인원이 장기간 관여하는 프로젝트라면, 위 표의 첫 번째 조건에 해당할 가능성이 높습니다. 다만 이 판단은 "Compose가 원래 그렇게 하라고 하니까"가 아니라, **팀이 실제로 Preview/테스트 프로세스에 투자할 것인지를 먼저 결정한 뒤** 따라와야 합니다. 투자 없이 구조만 흉내 내면 보일러플레이트만 남습니다.

## 3. 일회성 이벤트(Navigation/Toast/Dialog/BottomSheet) 처리 방식

### 3.1 이 문제의 본질: 이벤트를 "채널"로 볼 것인가 "상태"로 볼 것인가

Android/Compose 커뮤니티에서 이 주제는 지금도 의견이 갈립니다. 두 접근이 공존합니다.

**(A) 이벤트 채널 방식** — `SharedFlow`/`Channel` 등으로 "한 번 소비되면 끝인 신호"를 별도 스트림으로 흘려보내는 방식입니다(Orbit MVI의 `SideEffect`가 이 범주입니다). 상태와 이벤트를 개념적으로 명확히 분리할 수 있다는 장점이 있지만, 구독자가 없을 때(프로세스 재생성, 화면 회전 도중 등) 이벤트가 유실될 수 있고, 여러 컬렉터가 동시에 구독하면 각자 이벤트를 소비해버리는 문제가 알려져 있습니다.

**(B) 이벤트를-상태로 취급하는 방식** — "표시할 다이얼로그의 종류"나 "표시할 메시지"를 UiState의 nullable 필드로 두고, UI가 그 값을 소비한 뒤 `onConsumed()` 류의 콜백으로 다시 `null`로 되돌리는 방식입니다. 상태 기반이라 생존성(Configuration Change, 프로세스 복구)이 보장되지만, "언제 리셋할지"를 매번 명시적으로 챙겨야 하고 ack 처리를 빠뜨리면 같은 이벤트가 중복 소비되는 버그가 생기기 쉽습니다.

어느 쪽이 절대적으로 옳다고 업계에서 합의된 상태가 아닙니다. 신규 프로젝트라면 이 선택 자체를 먼저 팀 논의로 확정해야 하는 항목입니다.

### 3.2 두 방식 모두에서 변하지 않는 원칙

접근 (A)와 (B) 중 무엇을 고르든, 2장에서 다룬 원칙은 그대로 유지되어야 합니다 — **stateless 렌더러는 이벤트 소스(ViewModel, Effect 스트림)에 직접 의존하지 않는다.**

- (B)를 택하면 다이얼로그/바텀시트 표시 여부가 UiState의 일부이므로, 자연스럽게 stateless 계층(Content)에서 그대로 처리할 수 있습니다. "Screen이냐 Content냐"라는 질문 자체가 사라집니다.
- (A)를 택하면 이벤트 스트림을 구독하는 지점(stateful 계층)이 이를 로컬 상태로 변환해 stateless 계층에는 순수한 값만 내려줘야 합니다. 이 변환 지점을 stateless 계층 안으로 옮기면, stateless 계층이 다시 이벤트 소스에 의존하게 되어 2장에서 얻은 이득(Preview 가능성, 테스트 용이성)이 그대로 무너집니다.

즉 **"Dialog/BottomSheet가 Screen에 있어야 하는가 Content에 있어야 하는가"는 별개의 질문이 아니라, "이벤트를 채널로 다룰 것인가 상태로 다룰 것인가"라는 상위 결정의 하위 결과**입니다. 신규 프로젝트 설계 순서는 이벤트 처리 방식(A/B)을 먼저 정하고, 그 결과로 배치 규칙이 따라오는 것이 맞습니다.

### 3.3 선택에 영향을 주는 요인

| 조건 | 기울어지는 방향 |
|---|---|
| 프로세스 재생성·화면 회전 시나리오가 QA에서 중요하게 다뤄짐 | (B) 이벤트-as-state |
| 상태 관리 프레임워크가 이미 이벤트 채널 개념을 1급 시민으로 내장(Orbit MVI의 SideEffect 등) | (A) 채택 시 팀 러닝커브가 낮음 |
| "무엇을 언제 리셋했는지" 추적하는 보일러플레이트를 최소화하고 싶음 | (A) 이벤트 채널 |
| 이벤트 중복 소비·유실 버그를 원천 차단하고 싶음 | (B) 이벤트-as-state |

이 표는 결론을 내리기 위한 것이 아니라, 팀 논의에서 실제로 저울질해야 할 축을 드러내기 위한 것입니다. 상태 관리 프레임워크 선택(자체 구현 / Orbit MVI / Circuit / MVVM+StateFlow 등)이 먼저 정해지면 이 선택지도 상당 부분 함께 결정됩니다.

## 4. 참고 구현 사례 (Nevera 프로젝트)

아래는 위 원칙을 실제로 코드에 옮긴 한 가지 사례입니다. **이것이 정답이라는 의미가 아니라, Orbit MVI + (A) 이벤트 채널 방식을 택했을 때 2·3장의 원칙이 실제로 어떤 코드가 되는지 보여주는 예시**입니다.

- Screen(stateful)이 `collectAsState`/`collectSideEffect`로 ViewModel을 구독하고, Content(stateless)는 `uiState`와 Intent 람다만 받습니다.
- SideEffect(이벤트 채널)로 트리거되는 바텀시트는 Screen의 로컬 state로 받아 Screen 계층에서 조립합니다. UiState로 지속되는 다이얼로그(로그아웃 확인 등)와 Content 내부에서 완결되는 순수 UI 상호작용(인라인 편집 등)은 Content에 둡니다.
- 매우 단순한 화면(상태가 거의 없는 스플래시 화면)조차 이 구조를 동일하게 따르고 있어, 이 프로젝트 안에서는 "예외를 인정하지 않는 쪽"으로 이미 결정돼 있습니다. 신규 프로젝트가 반드시 같은 결정을 내려야 한다는 뜻은 아니며, 2.4~2.6절의 판단 기준으로 별도로 재검토해야 합니다.

세부 규칙과 코드 예시는 [`mvi-presentation-layer-structure.md`](./mvi-presentation-layer-structure.md)에 정리돼 있습니다.

## 5. 신규 프로젝트를 위한 결정 체크리스트

팀 논의에서 다음 질문에 먼저 답한 뒤 세부 규칙을 정하는 순서를 권장합니다.

1. 상태 관리 프레임워크로 무엇을 쓸 것인가 (Orbit MVI / Circuit / 자체 MVVM+StateFlow 등)? — 이 선택이 3장의 이벤트 처리 방식 상당 부분을 결정합니다.
2. 일회성 이벤트를 채널로 다룰 것인가, 상태로 다룰 것인가?
3. Preview를 디자인 리뷰·QA 프로세스에 실제로 사용할 것인가?
4. Compose UI 테스트/스크린샷 테스트에 투자할 것인가?
5. 컨벤션을 스캐폴드/린트로 강제할 수단이 있는가?

3~5번의 답이 모두 "예"에 가깝다면 stateful/stateless(Screen/Content) 분리를 기본값으로 강제하는 쪽이 합리적입니다. "아니오"에 가깝다면, 분리를 강제하기보다 팀이 실제로 필요를 느끼는 시점에 리팩터링하는 쪽이 더 현실적일 수 있습니다.
